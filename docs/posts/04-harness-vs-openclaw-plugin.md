# 同样做插件化，DeepSeek Harness 和 OpenClaw 为什么走了两条路？

> **系列**：AI实战落地 · 插件哲学（第 4 篇）
> **上篇**：[框架启动要 75 秒，但 AI 推理只用 0.8 秒](https://juejin.cn/post/7672975601435213875)
> **GitHub**：[ai-production-lab](https://github.com/ai-production-lab/ai-production-lab)

---

DeepSeek Harness 8 月 13 日开源，五天冲到近 4 万 star、3100 fork，仓库里已经堆了 12000+ 次 commit。社交媒体上讨论最热的两个词是「黑色鲸鱼」和「一切皆插件」——Agent 主循环、存储、沙箱、UI 全部以插件形式存在，运行时没有不可替换的特权内核。梁文锋团队把公式写成 **Model + Harness = Agent**：框架不决定模型能力，只决定模型能力怎么跑。

这套设计确实漂亮。但如果你最近也在跟 OpenClaw 的架构改造——MCP 无状态化，再加上 Plugin SDK 模块化——会撞上一个更有意思的现象：两个框架都在做插件化，路却完全相反。Harness 选择「一切皆插件」，OpenClaw 选择「核心特权 + 插件扩展」。

这不是审美分歧。这是 Agent 框架里最硬的一个选择：**你的核心，到底要不要保护起来？**

## Harness：微内核，任何一层都能换

DeepSeek Harness 建在 Cordis 上。这是一个 TypeScript 微内核，只做三件事：插件加载与卸载、依赖追踪、类型化事件分发。官方原话很干脆——没有需要打补丁的特权核心。LLM 调用、工具执行、沙箱、会话日志，甚至 Web UI，全部以插件注册进同一棵树。

解耦靠的是 Seam 三层：Service Definition（接口）、Provider（实现）、Consumer（消费者）。于是你可以不改任何工具定义，把本地 shell 换成远程沙箱，把本地模型换成 API。更激进的是，插件树支持热重载和层叠配置覆盖——运行时就能检查自己的插件结构，替换其中任何一块，系统不必停。

好处是灵活性被推到头。MIT 协议，零特权内核，任何层都可以被替换。社区很快就涌进 50+ 插件——从皮肤、`@` 引用文件，到给纯文本模型补视觉能力，再到创造模式里让 AI 自己写插件。它本质上是一个开发者实验场：你可以拿它拼出任何一种 Agent 形态，而不被框架的默认选择绑死。

产品侧也把这句话做实了。发行版自带四种模式，本质是同一棵插件树的不同装配：标准模式加载完整工具链；极简模式只留 bash 和文件编辑，用来在最小环境下跑基准；PTC（程序化工具调用）让模型一次吐出 TypeScript，把多步工具串成一段执行；创造模式在标准能力之上，还能检查当前运行时、在内存里试验插件组合，甚至生成新的模式预设。灵活性不是口号，而是四种 profile。

代价同样清楚。第一，学习曲线陡。YAML 配置对新手不友好，Seam 和插件生命周期需要一点架构功底。第二，这是 v0.1 开发者预览，官方已经说了，后面会有破坏兼容性的变更。第三，也是最要命的——当核心本身也是插件时，安全边界在哪？任何人都能替换 Agent 主循环，恶意插件理论上就能接管整个系统。社区里已经能看到更激进的用法：把带 `dsh-plugin` 标签的仓库地址丢给 Agent，临时放开全部操作权限，让它自己装插件、自己卸载。对新手很友好，也正好坐实这道张力——可替换内核一旦配上「一句话放开权限」，攻击面就不再是假想题。

## OpenClaw：核心是黑盒，插件待在用户空间

OpenClaw 走的是另一头。v2026.3.22 那次重构，把 Plugin SDK 拆成 80+ 个细粒度子路径，但核心内部代码对插件完全不可见。插件只能走公开 API，不能 import 内部模块，也不能绕过安全边界。

核心是有特权的。Gateway 管完整运行时：插件加载、频道实现、工具注册表、安全校验。插件生命周期有六个阶段（Discovery → Validation → Entry Resolution → Registration → Activation → Execution），Hook 有五种执行模式（void、modifying、claim、sequential、synchronous）。这些都是插件「参与」核心的方式，不是「替换」核心的方式。

对一个已经有 50+ 扩展、大量生产用户的框架来说，「核心不能被插件篡改」是特性，不是缺陷。你的插件不能把 Agent 主循环换成挖矿脚本，也不能绕过 Manifest 直接跑未审查代码。ClawHub 的分发还有 JSON Schema 校验，不必执行第三方代码就能先看元数据。

代价是灵活性被收住。你不能在运行时替换 OpenClaw 的调度器，不能热重载插件（得重启），也不能把 Gateway 本身换成另一个实现。如果你想做根本性的架构实验，OpenClaw 不是正确的工具。

## 两条路，差在一个问题

写插件时，手感也不一样。写 Harness 插件，你是在定义一组 Seam：声明自己提供什么、消费什么，然后交给 Cordis 编排。写 OpenClaw 插件，你是在 Gateway 给的生命周期里注册回调——Discovery 声明能力，Registration 注册工具，Activation 准备资源。前者像写一个独立微服务再挂到服务网格，后者像在 Spring 里写一个 Bean，生命周期交给容器。

把两者叠在一起，分歧只剩一句：**核心是「可被替换的服务」，还是「不可侵犯的边界」？**

还有一层常被混为一谈：Harness 强调运行轨迹透明——每一步工具调用、读过哪些文件都能看见；OpenClaw 强调插件隔离——插件碰不到核心内部。前者是可观测性，解决的是信任与调试；后者是权限边界，限制的是插件能干什么。看得见 Agent 在做什么，并不等于插件换不掉内核。

| 维度 | DeepSeek Harness | OpenClaw |
|------|------------------|----------|
| 设计哲学 | 一切皆插件（含核心循环） | 核心特权 + 插件扩展 |
| 微内核 | Cordis（加载 / 依赖 / 事件） | Gateway（完整运行时） |
| 核心可替换 | 可以，任何层都能热替换 | 不可以，核心是黑盒 |
| 接口模式 | Seam 三层（定义 / 实现 / 消费） | 子路径导出 + Hook 五模式 |
| 热重载 | 原生支持 | 暂不支持 |
| 安全边界 | 主要靠插件自律；可一句话放开权限让 Agent 自装插件 | 强制隔离 + Schema 验证 |
| 透明与隔离 | 轨迹可见（可观测性） | 核心不可见（权限边界） |
| 适用阶段 | 探索期 / 实验 | 生产期 / 规模化 |
| 生态阶段 | v0.1，很快 50+ 插件 | 成熟期，50+ 已验证扩展 |

先例也分两边。Harness 更像 Eclipse OSGi 和 Emacs：几乎没有不可替换的内核，模块热插拔、动态装配。OpenClaw 更像 VS Code、macOS/XNU 和 Kubernetes：底下有明确的特权层，扩展跑在用户空间，你不能在运行时把内核换掉。

## 什么时候选哪条

三个判断就够用。

**你在探索，还是在生产？** 如果 Agent 长什么样还没定——主循环、工具协议都还在试——Harness 的「一切可替换」能让你少付试错税。如果已经有生产流量和 SLA，OpenClaw 式的核心特权给你的是可预测性和安全兜底。

**插件生态有多大？** 扩展还不到你能逐一 review 的规模时，微内核风险可控。一旦第三方多到你开始害怕发版，就需要强制边界——因为一个失控插件就可能拖垮整棵树。OpenClaw 在 50+ 扩展时已经把「技术债」写成了「核心不可见」，不是没有原因。

**用户是谁？** 框架开发者、架构师、想改 Agent 行为的人，会为 Harness 的灵活性买单。只想开箱即用、不关心内核的人，更吃 OpenClaw 的边界清晰和 ClawHub 一键安装。

## 它们现在不像，以后未必不像

把时间轴拉长，这两条路未必永远分叉。Harness 要从 v0.1 走进生产，迟早会撞上安全问题——「任何层都可替换」在规模化之后就是攻击面，它会开始加权限模型和强制边界。OpenClaw 要从特权核心长出更活的生态，也迟早得补某种热更新和动态加载。

这不是谁对谁错。这是同一条生命周期上的两个坐标：探索期要灵活，生产期要稳，成熟期再在中间找平衡。DeepSeek Harness 现在停在探索期；OpenClaw 刚走完「从能跑到能上生产」的那一刀。它们不是对手，只是还没走到同一个点。

所以，回到开头那个问题：你的核心到底要不要保护起来？

没有标准答案，但每个做 Agent 框架、做插件系统、做内部平台的人都值得认真答一次。「一切皆插件」相信没有任何设计天生正确，一切都该能被替换；「核心特权」相信有些边界一旦立下就不该被拆，因为拆掉的代价由整个生态承担。

你正在做的系统，核心是可被替换的服务，还是不可侵犯的边界？这个问题，你答得上来吗？
